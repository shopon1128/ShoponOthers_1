# Debug Discipline — デバッグの規律

デバッグの失敗は、能力不足ではなく手順の省略から生じる。
このスキルの目的はひとつ: **「直ったように見える」ではなく「原因を特定して直した」で終わる。**

---

## 原則0: 再現が先、修正は後

- 修正に手を付ける前に、**バグを確実に再現させる手順**を確立する。再現できないバグは、直せたかどうかも検証できない
- 再現手順は具体的に書き留める(入力・操作・環境・頻度)。「たまに起きる」なら、起きる条件を狭める作業が最初のタスク
- どうしても再現できない場合は、修正を試みるのではなく**観測を仕込む**(ログ・アサーション・値のダンプ)ことを提案し、次に起きた時に情報が取れる状態を作る

## 原則1: エラーメッセージを最後まで読む

- スタックトレースは飛ばし読みしない。**最初に発生したエラー**(後続のエラーは連鎖のことが多い)と、**自分のコードに最も近いフレーム**を特定する
- エラーメッセージ・ファイル名・行番号は、たいてい原因をそのまま言っている。メッセージを読む前に推測を始めない
- ログ・コンソール・標準エラーなど、既に出ている情報を全部集めてから仮説を立てる(reality-check 原則1: 記憶より現物)

## 原則2: 仮説は一度に一つ

- 変更は**1回に1箇所**。変更→再現手順を実行→効果を確認、のループを守る
- 効果が無かった変更は**元に戻してから**次の仮説へ。戻さずに重ねると、直った時に何が効いたのか分からなくなり、無関係な変更がコードに残る
- 複数箇所を同時に変えて「どれかが効いた」状態を作らない(散弾銃デバッグの禁止)
- 各仮説は検証前に一文で言語化する: 「◯◯が原因なら、△△すれば□□になるはず」。予測と結果が食い違ったら、仮説を修正してから次へ

## 原則3: 二分探索で狭める

原因の場所が分からない時は、勘で飛び回らず探索空間を半分に割る:

- **どの層か**: 入力データか、処理か、出力か。途中の値をダンプして正常/異常の境界を見つける
- **いつからか**: 動いていた版があるなら `git bisect`(または手動で中間のコミットを試す)
- **どの部分か**: 処理を半分無効化して再現するか確認、を繰り返す
- **最小再現**: 再現する最小のコード・データまで削る。削る過程そのものが原因を炙り出す

## 原則4: 症状を消すな、原因を消せ

- try/catchの追加、nullチェックの追加、sleep/待ち時間の挿入、リトライで**症状が見えなくなる**のは修正ではない(原因はまだそこにいる)
- 「とりあえず動くようになった」状態で手を止めない。なぜその変更で動くようになったのかを説明できるまでが調査
- 対症療法が本当に必要な場面(外部要因・締切)では、対症療法であることと残存リスクを明示して報告する

## 原則5: 「なぜ直ったか」を説明できて完了

修正後、以下がすべて言えるか確認する:

1. **原因**: 何が、どういう仕組みでこの症状を起こしていたか
2. **修正**: なぜこの変更でその仕組みが断たれるのか
3. **検証**: 再現手順が再現しなくなったことを実際に確認したか(reality-check 原則2)
4. **影響**: この修正が壊しうる他の箇所を確認したか

説明できない修正は偶然であり、バグはおそらくまだ生きている。「原因不明だが再現しなくなった」場合は、そのまま完了にせず**その事実を報告**する。

## 原則6: 撤収まで含めてデバッグ

- 調査用に入れたログ出力・コメントアウト・実験コードは、修正確定後にすべて除去する(残す価値があるログは意図的に残すと明示する)
- 除去後にもう一度、再現手順と既存の動作確認を実行する(掃除で壊すのは典型事故)
- プロジェクトに `LESSONS.md` があれば、原因・解決・教訓を追記する(15分以上かかった調査は記録に値する)

---

## アンチパターン(これを見たら止まる)

- エラーメッセージを読み切る前にコードを書き換え始める
- 「たぶんここだろう」で複数箇所を同時に修正する
- 効かなかった変更を戻さずに次の変更を重ねる
- try/catch・nullチェック・sleepで症状を隠して「直りました」
- 再現手順を確立せずに「直したはず」と報告する
- 直った理由を説明できないまま完了扱いにする
- 調査用のprintデバッグをコードに残したまま納品する

## 完了前の最終チェック(30秒)

1. **再現**: 修正前に再現手順を確立したか
2. **単一性**: 有効だった変更は特定できているか(不要な変更が混ざっていないか)
3. **説明**: 原因→修正→なぜ直るか、を一続きで説明できるか
4. **検証**: 再現手順の消滅と、周辺への無影響を実際に確認したか
5. **撤収**: 調査の痕跡を除去し、除去後にも動作確認したか

5つすべてに即答できないなら、まだ完了ではない。
