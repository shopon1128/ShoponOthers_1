# Code Design Review — 書いたコードの設計を見直す

「動く」と「変更に耐える」は別の性質で、テストが通っても後者は保証されない。そして実装した直後は、自分の設計の弱点が最も見えにくい。書いた理由を知っているので、コードに書かれていない意図で穴を埋めて読んでしまうからだ。
このスキルの目的はひとつ: **観点を固定して、書いたコードを「次の変更」の目で読み直す。**

---

## 誰がレビューするか

| 変更の規模 | レビューする人 |
|---|---|
| 1〜2ファイル、新しいクラス・モジュールなし | 自分で下の観点を順に通す |
| 新機能 / 新しいクラス・モジュール / 3ファイル以上 | 会話の経緯を持たないサブエージェントにレビューさせる(末尾のテンプレート) |

サブエージェントに渡すのは**要件と対象ファイルだけ**にする。設計の経緯や言い訳を渡すと、書いた本人と同じ読み方になり、別の目を用意した意味がなくなる。

## 観点(重要な順)

1. **変更シナリオ試験**(最重要): このコードに来そうな変更を2つ、具体的に想定する(例: 敵の種類を1つ足す / 保存形式を変える / 画面を1枚増やす / 集計の列を1つ増やす)。それぞれで触るファイルを列挙する。1〜2か所に収まれば良い境界、あちこちに散らばるなら境界が悪い
2. **責務**: 各クラス・ファイルの責務を1文で言えるか。「〜し、さらに〜もする」と「と」でつながるなら分割候補
3. **依存の向き**: 安定したもの(ルール・データ定義)が、変わりやすいもの(UI・入出力・エンジンやフレームワークの API)に依存していないか。循環依存はないか。部品が自分の外側(親・呼び出し元・シーン全体)を探しに行っていないか
4. **状態の置き場所**: 同じ事実を2か所で持っていないか(二重管理は必ずいつか食い違う)。その状態を誰が書き換えられるかを、コードから答えられるか。グローバル・シングルトン経由でどこからでも書き換えられる状態はないか
5. **データとロジックの分離**: 調整値・テーブル・文言がロジックに埋まっていないか。データだけ差し替えたいときにコードを触る必要があるか
6. **抽象化の量**:
   - 早すぎる: 実装が1つしかないインターフェース、使われていない設定項目、深さ1で終わる継承
   - 遅すぎる: 種類ごとの分岐(switch / if-else の連鎖)が3か所以上に散っている。種類を足すたびに全部を探して直すことになる
7. **重複**: 同じ知識(ルール・定数・計算式)が複数箇所にないか。ただし見た目が似ているだけのコードは重複ではない。変わる理由が違うなら、別物として残すのが正しい
8. **名前**: 名前が役割を表しているか。`Manager` `Helper` `Util` `Data` `Info` のような何でも入る名前は、責務が曖昧な兆候
9. **エラーの境界**: エラーをどこで検出し、どこで扱うかが一貫しているか。途中で黙って握りつぶしていないか

## 深刻度

- **重大**: 今後の変更でほぼ確実に壊れる、または書き直しになる(二重管理、循環依存、外部に公開したインターフェースやデータ形式の誤り)
- **重要**: よくある変更のたびに複数箇所へ手が入る
- **軽微**: 名前・配置・細かな重複

すべてを重大にしない。深刻度が正直でないレビューは、本当に重大な指摘を埋もれさせる。

## 出力形式

```
### 変更シナリオ試験
- シナリオ1: <想定した変更> → 触るファイル: <列挙> → 判定
- シナリオ2: ...

### 指摘
#### 重大 / 重要 / 軽微
- <file:line> 問題: <何が> / 効く場面: <どの変更で困るか> / 直し方: <方針>

### 見送った観点
- <観点>: <見送った理由>(1行ずつ。何も見送らなかったなら「なし」)

### 判定
<このまま完了でよい / 直してから完了 / 設計からやり直し> — <理由を一文で>
```

問題が見つからなかった場合も「良い設計です」で終わらせない。変更シナリオ試験の結果を根拠として示す。

## 指摘が出た後

- **今回自分が書いたコード**の重大・重要な指摘は、直してから完了を報告する。直したら変更シナリオ試験をもう一度通す
- **今回のスコープ外の既存コード**の問題は直さず、一行で提案する
- 直さないと判断した指摘は、理由とともに完了報告に書く。黙って捨てない

## アンチパターン(これを見たら止まる)

- テストが通ったことを設計が良いことの根拠にする
- 変更シナリオを「将来いろいろ変わるかも」のように抽象的なまま済ませる(具体的な変更を1つ名指ししないと試験にならない)
- 自分が書いた直後のコードを、書いたときの意図を思い出しながら読む(サブエージェントに回すべき規模なのに自分で済ませる)
- 指摘を受けて、スコープ外のリファクタまで一緒に始める

- 判定を一文で言い切る
