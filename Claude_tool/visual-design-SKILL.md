# Visual Design — 見た目の設計

生成された見た目が「ダサい」「AIっぽい」と感じられる原因の多くは、下手さではなく**既定値のまま**であることにある。どの題材でも同じ配色・同じカード・同じ飾りが出てくる。
このスキルの目的はひとつ: **既定値ではなく、この題材・この読者のための選択をする。**

---

## 0. 既存の決まりを探す

- プロジェクトに DESIGN.md・デザイントークン・CSS 変数・ブランドガイド・既存の画面があれば、それが最優先。新しい方針を出さずに従う
- 依頼文で方向が指定されていれば、それに従う(下の「既定の見た目」に当たる指定でも、依頼が優先)
- Web なら、プロジェクトの `web-dev.md` も読む

## 1. 題材と読者を決める

- 何のためのものか、誰が見るか、見た人に最初に何をしてほしいか。依頼から分からなければ、仮説を1つ立てて提示し確認する
- 見た目の個性は、題材の世界(業界・素材・道具・言葉づかい)から引き出す。8〜11歳向けのおもちゃと金融アナリスト向けの画面では、正解がまったく違う
- 実際の内容で作る。ダミー文(「ここにテキスト」)のまま作った見た目は、内容が入ると崩れる

## 2. コードの前に方針を決める

次の4つを短く書き出してから作る:

- **色**: 役割付きで4〜6色(背景 / 文字 / 主色 / アクセント / 意味色)を hex で
- **書体**: 和文・欧文の書体と、それぞれの役割。系統は1〜2つまで。2つ使うなら明確に違うものを
- **レイアウト**: 1文の説明と、ASCII のワイヤーフレーム。揃え(左揃え・中央揃え)も決める
- **この題材ならではの一点**: 見た人の記憶に残す要素を1つだけ決める

参考が欲しいときは `~/正倉院/Claude/道具箱/design-md-jp/design-md/`(日本のサービスの DESIGN.md 集)から題材の近いものを2〜3件読む。特に和文の組版(フォントの指定・行間・字間・禁則)と余白の取り方が参考になる。ただし特定ブランドの配色・ロゴ・固有の意匠はそのまま写さない(他社の見た目になる)。方針を残すなら `design-md-jp/template/DESIGN.md` の形式が使える。

## 3. 方針を「既定の見た目」と照合する

AI が作る見た目は、次のパターンに寄りやすい。どれも題材によっては正当だが、題材と関係なく出てくるなら、それは選択ではなく既定値である:

1. 生成り色の背景(#F4F1EA 付近)+ コントラストの強いセリフ体の見出し + テラコッタ系のアクセント
2. ほぼ黒の背景 + 蛍光緑や朱色のアクセント1色
3. 細い罫線・角丸なし・新聞風の段組み
4. すべてを同じ角丸・同じ薄い影のカードに詰める。装飾のためのグラデーション
5. 題材と無関係に付く飾り: 見出しの上の全大文字の小ラベル、「A · B · C」の中黒区切り、リンク末尾の「→」、等幅フォントの小ラベル、順序でない内容に振った 01 / 02 / 03
6. 見出しの一語だけ色や斜体を変える
7. 全セクションが下からふわっと出るアニメーション、全カードのホバー演出
8. 大きな英語の見出しに小さな日本語訳を添える二段見出し

照合の方法: 「同じ依頼を別の題材で受けたら、同じ方針になるか」を考える。なるなら、その部分は既定値なので作り直す。何をなぜ変えたかを一言添える。

## 4. 作る

- **大胆さは1か所に**。記憶に残す一点以外は静かに整える。仕上げの前に、装飾を1つ削る
- **構造は情報**。枠・罫線・番号・ラベルは、内容の構造を表すときだけ使う。飾りとして置かない
- **動きは控えめに**。自動で動く演出は、注意を引きたい1か所だけ。ユーザーの操作への反応(開く・確定する)として何が変わったかを示す動きは歓迎
- **文字組み**: 本文の1行を長くしすぎない(欧文は80字未満、和文も1行が長いと読みにくい)。セリフ体・和文の本文は行間を広めに取る
- **CSS の詳細度**: `.section` の余白と `.cta` の余白が打ち消し合うような衝突に注意する

**品質の最低線**(言わずに満たす):

- スマホ幅まで崩れない
- キーボードのフォーカスが見える
- `prefers-reduced-motion` を尊重する
- 文字と背景のコントラストを計算で確かめる(WCAG AA: 本文 4.5:1、大きな文字 3:1)。見た目の印象で判断しない

**文言も設計の一部**:

- 仕組みの言葉ではなく、ユーザーの言葉で書く(「Webhook 設定」ではなく「通知の設定」)
- ボタンは押すと何が起きるかを言う(「送信」より「変更を保存」)。同じ操作は流れ全体で同じ名前にする(「公開」ボタン → 「公開しました」)
- エラーは、何が起きてどうすれば直るかを書く。空の画面は、次に何をすればよいかの案内にする

## 5. 見て、直す

- 表示できる環境なら、スクリーンショットを撮って方針と照らして批評し、直す。デスクトップ幅とスマホ幅の両方を見る。コードを読むだけでは見た目は分からない
- 見られない環境(Unity のゲーム画面など)では、「どの画面で何が見えれば正しいか」を具体的にユーザーに依頼し、見た目は「未確認」と報告する

---

## アンチパターン(これを見たら止まる)

- 方針を決めずに、いきなり HTML / CSS を書き始める
- 題材を確かめないまま、きれいに見える汎用のテンプレートを当てはめる
- 目立たせたい要素がいくつもあり、どれも目立たない
- スクリーンショットを見ずに「きれいに仕上がりました」と報告する

## 納品前の最終チェック(30秒)

1. **既存**: DESIGN.md や既存の画面など、従うべき決まりを確認したか
2. **方針**: 色・書体・レイアウト・記憶に残す一点を、コードの前に決めたか
3. **照合**: 方針を既定の見た目と照らし、変えた点を言えるか
4. **最低線**: スマホ幅・フォーカス・動きの抑制・コントラストを確かめたか
5. **目視**: 実際の見た目を見たか。見られないなら「未確認」と書いたか
